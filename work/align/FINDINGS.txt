2. root:19A9: a mis-framed boundary, not an alignment exception
---------------------------------------------------------------
The three unreferenced retf at 19A95/19A96/19A97 are the last three (empty) functions of the index
module root:1986.  1986 therefore ends at the even address 19A98, and 19A9 starts at 19A9:0008 = 19A98.
It is word aligned and needs no fill.
* The rows 19A9:0005-0007 were framed by arithmetic only.  Nothing references them.  Frame 19A9 is
  attested only from 0008 on (S27 far pointer at 59224; far calls to 000B, 001D, 0310, 031D).
* Win16 index TU (MAPSYM order): OpenIndex, CreateIndex, CloseIndex, FindIndex, DeleteCurrentIndex,
  AddIndex, DeleteIndex.  DOS 1986 has OpenIndex, CreateIndex (1-byte retf: the read-only build empties
  the write side), CloseIndex and FindIndex, then exactly three 1-byte retf.  19A9 stubs its write side
  differently (Punt "READ-ONLY run": DBAdd, DBDelete, DBPack).
* Linker experiments (exp.py, exp.json) used MS LINK 5.10 and RTLink/Plus 6.10 with pinned hashes.
  Both linkers gave identical results in all seven variants.
  - accepted split: 00 fill inserted (the accepted layout is not linker output);
  - 3 stubs in 1986: reproduces the original;
  - 1 stub in 1986: reproduces the bytes too, but is rejected on the Win16 member count and the stub style;
  - /NT DB_TEXT shared by both files: one combined segment, so one frame, which contradicts frames 1986
    and 19A9 and the relocated far call at 19AC1 -> 1986:012A (TU-1).  The fill is still inserted;
  - #pragma alloc_text: the second segment is WORD too, so the fill is inserted;
  - MASM 'segment byte': the only variant with no fill.  It is excluded because 19A9 is MSC 6.00AX
    output (DBRecall, _DATA/CONST, /Zi records);
  - MASM 'word' control: the fill is inserted.
* Gate check: the corrected source work/align/m19A9.c (without the stubs) binds exactly at
  19A98:19DC7.  promote --verify-only on the live tree shows every claim, _DATA, CONST and the whole
  segment exact.  The only refusal is the function-table rows 19A9:0005-0007, which the reframe moves.

3. root:2CFB: MEMHOOK_TEXT was read after the runtime library search
-------------------------------------------------------------------
* exp2 (MS LINK 5.10 + RTLink 6.10):
  - listed as a FILE: MEMHOOK_TEXT lands before _TEXT (the t3 result);
  - in MH.LIB searched after LLIBCR, LIBH: after EMULATOR_TEXT, as in the original;
  - library searched first: before _TEXT;
  - RTLink FILE after LIBRARY: before _TEXT.
* Class hypothesis excluded (exp3, overlaid RTLink 6.10 link).  A non-CODE class, or a class ending in
  CODE, moves the segment behind the overlay areas into the resident data section together with
  C_ETEXT.  In the original, C_ETEXT is at 3D57:0000: crt0's DBDATA base16 word at S27 5D8F0 is 3D57.
  MEMHOOK_TEXT is in the root at 2CFB2.
* exp4: RTLink 6.10 accepts "LIBRARY LLIBCR, LIBH, R2CFB.OBJ" and places MEMHOOK_TEXT exactly like the
  original.  The tools/rtlink.py patch uses this.
* LIB.EXE (msc-6.00/BIN, sha256 418aec41...36ff3, not pinned) was used only for these experiments.

4. Patch proposal (NOT installed; work/align/patch/, base md5 in base/MD5SUMS)
--------------------------------------------------------------------------------------
* tools_modules.py -> tools/modules.py: code_alignment_reasons = rule CODEALIGN-1.  It applies in
  verify_extent at the extent start, and in verify_module at the origin of a later object that has no
  extent.  It reads the SEGDEF alignment, so a BYTE MASM segment may start at an odd address.
* tools_promote.py -> tools/promote.py: --drop-extent WHY (journaled with the old extent).  Without it
  the correction is circular.  functions.py reframe refuses claimed rows, and the corrected extent is
  refused while the old rows exist.
* tools_rtlink.py -> tools/rtlink.py:
  - late root objects go into the LIBRARY list after LLIBCR, LIBH;
  - run_link reads the pin from toolchain.json 'linkers'.  Today compiler.verify_profile('rtlink610')
    raises KeyError, so tools/rtlink.py cannot run the link.
* tests_test_codealign.py -> tests/test_codealign.py, T13_m19A9_odd_start.c -> tests/negatives/:
  - rule unit tests (word, byte, paragraph, none);
  - oracle invariant (no contiguous odd frame start);
  - negative control on real data: the old 19A9 file at 19A95 is refused by CODEALIGN-1 alone, with
    every claim individually exact;
  - positive control at 19A98;
  - --drop-extent refusals and a verify-only positive.
* Order: install the patch, run migrate.sh (4 steps: promote 19A9 --drop-extent + release stubs;
  functions.py reframe root:19A9:0005/6/7 -> 1986; promote 1986 --claim f_1986_0235..0237;
  promote 19A9 --extent 19A98:19DC7), then validate.  With the patch but without the migration,
  validate refuses root:19A9, as intended.
* Drafts: m19A9.c, m1986.c.  The stubs keep placeholder names.  Win16 candidates by position:
  DeleteCurrentIndex, AddIndex, DeleteIndex (content-free bodies: needs a reviewed decision).
