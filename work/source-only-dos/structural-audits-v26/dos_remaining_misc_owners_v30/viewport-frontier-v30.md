# Viewport bounds for cache owners 15C4 and 1114 (v30)

Status: **root-false; no admission or canonical edits**. This scratch note answers the layout question before any 15C4 storage admission and preserves the prior v26 receipt unchanged.

`fd_50F6_1114` has the bounded path: the 156-source audit finds reads/writes only in `f_0250_129E`. That function rejects `x < 0`, `y < 0`, `x >= 40`, or `y >= 30` before computing `i = y * 40 + x`; its reached byte indexes are therefore 0–1199. The loop around it can follow dynamic viewport dimensions, but that route does not bypass the fixed per-cell guard. Its 30x40 byte view remains footprint-bounded by current source evidence.

`fd_50F6_15C4` does not have the same result. `f_0250_129E`, `DrawSpider`, and `DrawBalloons` have fixed-domain guards, and `f_0250_05CB` clears exactly 0x960 bytes. However, `ZapEuMapAt` writes `[v][h]` after comparing `h` and `v` to the dynamic globals `fd_50F6_10E0/10DE`; `InvalEuMap` writes with stride 40 after only the same dynamic bounds (plus world-coordinate clips). Neither function proves the dynamic width <= 40 and height <= 30.

The dynamic dimensions come from `f_0250_0E15`: it calls `win_GetObjRect(4)` and divides that live rectangle by `g_19BE/g_19C0`. This is refreshed by the win-0 draw hook and the window open/geometry-change callbacks. `DoMapUpdateDraw` is empty; `DoEditAndMapUpdateDraw` then calls `DoEditUpdateDraw`. These names provide no independent fixed viewport bound.

For a concrete baseline, the read-only parser uses the pinned HCEGANT index exactly as `OpenIndex` does (20-byte header, then count 8-byte entries) and reads only typed fields from the uncompressed window-0 kind-0 and kind-9 records. Kind 9 supplies `[14,22,404,325]` for root window 0. `win_LoadWindow` applies this to object 0, and the source layout constraints yield object 4 `[64,41,416,330]`, or 352x289 pixels: 22x19 tiles at 16px, 29x25 at 12px. The baseline fits the cache, but this is conditional resource data. The root window's HCEGANT flags are 0x050E: resizable bit 0x0008 set, 0x1000 screen-clamp bit clear. The reachable resize event path adjusts root width/height, runs `win_Recalc`, and calls the geometry-change hook. The resize helper does not impose a bottom-edge cap when bit 0x1000 is clear; a fixed 30-row bound is not established by the checked-in baseline resource or source.

The `winheaders` allocation in `f_00BA_0002` is excluded as geometry evidence: the 0x100 bytes become `fd_50F6_10CC`, which `ShowIntro` consumes as CustomerID material. The actual initial `win_offsets` source is the selected database's `(g_5A97, kind 9)` record. Alternate database packages and their object layout remain outside the HCEGANT observation.

`0150` is not an accepted exclusion. It was omitted from the nine-target v26 receipt because it belongs to a separate sound-record candidate: `f_0000_0149` appends a far pointer at `fd_50F6_0150[g_181C++]`, with a source check allowing 39 slots. The durable v21 sound review still says `root_reviewed=false` and `admitted=false`, so if the original assignment includes 0150 it remains separately open.
