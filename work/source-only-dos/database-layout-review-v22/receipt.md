# v22 database Punt boundary review

**Result: `ROOT_FALSE_UNRESOLVED`.** Keep `database-open-minus-one-record` and `database-handle-plus-four` unchanged and unresolved. This is a source-only closure review, not an admission or a claim that the gates can close.

The bounded no-free frontier is a fifth active database open from `main`: optional `language`, required `shared`, optional `lrshare` for selector 2 or 4, then the one display database opened by `f_205F_0004`, followed by `db_SetDataBase("sound")`. Missing either optional predecessor leaves a free record. The claimed four-record frontier therefore requires every predecessor open to **return successfully** and requires that no earlier first `Punt` returns to startup. Four attempted calls alone do not establish it. `db_SetDataBase` stores the `OpenDB` result before incrementing the count and testing for a negative handle.

The main success-only call inventory is closed in the captured effective source rows: `OpenDB` is called only by `db_SetDataBase`; `GetFreeHandle` only by `OpenDB`; `IBMInitStuff` is called only by `main`; `f_205F_0004` is called once by `IBMInitStuff`; and there is no source call or address-taking of `db_CloseDataBase`. `CloseDB` is only called inside `db_CloseDataBase`. The layout symbol registry has five aliases for the database functions and one for `IBMInitStuff`; none is referenced in the effective generated source rows. There is no repeated display setup or source-reachable pre-sound database close in this bounded startup path.

The counterexample to a broad first-`Punt` closure occurs before display setup. `IBMInitStuff` can reach `db_SetDataBase("shared")` before `f_205F_0004`; a database open or index failure can call `DosPunt` and then `Punt`. The callback owner has no initializer, and its slot-zero alias is `g_9128`. The only source initialization is `f_1B4E_0025`, called inside `f_205F_0004`, after these opens. Thus the early first `Punt` performs an indirect far call through source-zero `g_9128` to `0000:0000` as code, before reaching its fatal helper. The external behavior of that invalid call is unproved. This review reads no physical IVT bytes and does not infer a linker neighbor. `Punt` sets its private guard before the call; if this early path returns to startup, the guard remains set, and the later full-handle `Punt` takes the recursive immediate-return branch. `OpenDB` then proceeds at record index `-1`; if it returns `-1`, `db_SetDataBase` writes `db_handles[4]` before checking the value. This unresolved return/termination boundary prevents closing either access.

When the four prior database opens do return successfully without any earlier `Punt`, the fifth-open `Punt` is the outer first `Punt` after `f_1B4E_0025` has installed its 25 no-op default callback targets and the display setup has run. Its fatal cleanup is source-accounted: `g_2BD4` begins at 1 and `fd_55B3_610A` at -1; the channel cleanup reads the `4A4E.type` sentinel from the admitted zero-startup 33-by-6-byte owner; `StopSong` skips because `g_756E` begins at zero; cleanup checks all 56 admitted zero-startup six-byte Voice rows and finds `kind == 0`; and saved sound word zero selects `g_68DA[0]`, the empty `f_277E_0938` routine. The cleanup then calls `f_28BC_04E0(0)`. That is a real PIT/DOS-vector operation restoring INT 08h from the source-owned zero `old_int8` field, not a no-op. The timer effect stays explicit; the fatal-path DOSBox comparison remains a separate execution-acceptance check.
