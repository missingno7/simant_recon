# FAR_BSS word closure v34

**Disposition:** the evidence supports the scalar type and shape of five independent signed 16-bit source-state words, and supports a proposed zero-initialized source owner for each. No concrete enclosing-provider, indexed, or SaveRec route requires a wider owner. The current intake does not yet define these words, and this review does not establish emitted COMDEF extents, source startup-zero behavior, or lifetime independence. The map-bound pair has a specific producer/setup question: active code consumes it as right/bottom map bounds, but the inspected game code does not assign either word.

The locked executable's entire 19,408-byte FAR_BSS image is zero, so the original image contains `0000` at each target. This is not proof that a future source-defined object has been emitted or zeroed, and it is not a permanent-zero claim. The current intake has no owner definition for these words, is `INCOMPLETE`, has no standalone DOS executable, and records `NOT_EXECUTED`. A candidate natural uninitialized `int far` owner would still need its exact emitted extent and startup-zero evidence admitted. The two-byte next-symbol gap is not used as object-size evidence.

No provider, reviewed alias, SaveRec span, or target-address escape contains it. | Signed-word bound view supported; historical backing extent and a nonzero setup value remain open. |

The dimension-like pair is used as actual map-bound input, not merely as unexplained offsets: `InvalEuMap(left, top, right, bottom)` clamps `right` to 127 and `bottom` to 63, then iterates both endpoints inclusively. Passing `(0,0,0FB6,0FFA)` therefore supplies right/bottom coordinates; zero values reduce the requested rectangle to cell `(0,0)` when the viewport predicate permits a dirty-cell write. `SetMapPlane*` also subtracts `0FB6` from fixed 128/64 scroll limits, and root:004A centers related map UI positions using halves of both values. Their use is conditional on map/plane and window state in some paths, but `RandWorld` and S22 `SetAlarmDropState` are real callers and `InvalEuMap` is an active routine. `UpdateEdit` only draws when `win_IsWinOpen(0)`; `CenterEdit` performs real coordinate calculations and calls its clamp helpers. The no-op `f_0250_0ED2` and `MakeDMap` do not make `InvalEuMap` a stub. Thus “optional editor state” is possible for some effects, but the actual bound semantics are evidenced and a value-producing setup route remains specifically unresolved.

## Scope and limits

- The v33 original sweep covers all 1,730 function rows in 28 units and explicitly includes S22 `SetAlarmDropState`; it records 1/2/3/12/10 direct reads respectively and zero direct stores for the five words. The v34 frame-aware `tools.dataref.far_refs` pass groups the same 1,730 rows into 122 `(unit, segment)` groups and resolves 623 distinct FAR_BSS displacement offsets. Direct target reads resolve through relocation-backed `CONST DG` words; the exact words and users are in [frame-sweep-v34.json](frame-sweep-v34.json). Because that helper does not reconstruct a register's computed base, the indexed `DrawSwarm` and balloon cases above were separately checked in default non-raw `context.py` output.
- Current intake has 186 compiled objects, 191 symbolic aliases, 59 provider proofs, and 370 measured FAR_BSS COMMUNAL extents; none intersects any target. Its 26 reviewed data aliases contain no `50F6` alias. The earlier complete owner/view scan checked 454 extents with no target intersection. The explicit 307-payload-row S09 SaveRec table has no target overlap. Current intake source paths are the same 156-file set pinned by v32/v33; all 1640 effective game functions have dispositions, while the intake remains incomplete for executable/runtime acceptance.
- Direct target fixups and users are pinned in the frame sweep. The bounded candidate array routes are also backed by registered provider extents and non-raw instruction contexts: the balloon arrays use relocated far-segment words, and `DrawSwarm` forms `BX = si + 0xF84` / `si + 0xFC6` before its byte accesses, with `si < 16`.
- No source code, canonical file, manifest, journal, or frozen v33 artifact was changed. The only new files are in this v34 worker directory.
