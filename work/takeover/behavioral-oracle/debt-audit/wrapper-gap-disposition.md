# Follow-up: materialized references and callable-gap behavior

This follow-up is read-only with respect to historical ownership. It does not edit the function inventory, extend/trim known extents, or claim that lack of a static reference proves dead code.

## Pointer-materialization control

`scan_code_materialization.py` decodes every instruction in the 1,730 known original function extents and searches for every offset-field occurrence of the seven gap addresses. It qualifies near branches by the actual containing unit/CS frame, checks exact far control-transfer operands, offset-field loader relocations, adjacent segment relocations/`mov reg,CS` context, and source identifiers/labels. The result is pinned in `code-pointer-materialization.json` and summarized in `code-pointer-materialization.md`.

No known extent materializes an exact far pointer to one of these seven addresses using `mov reg,offset; mov reg,seg`/fixup, split stores, a far call/jump, or an adjacent-segment relocation pattern. No exact offset-field loader relocation names a gap entry. Hits that look similar are frame-mismatched near branches, common constants/register loads, or same-unit code references with different CS frame. No accepted module source has a local/private label, direct call, or address-taking spelling naming one of the gap addresses. This closes the specified forms of materialized-pointer scanning over known function bodies, but cannot exclude data-driven values, unknown/unowned code, or runtime arithmetic; it is not an unreachable/dead-code proof.

## Supplemental-address natural-C experiments

The three wrapper candidates are whole-module drafts under `wrapper-drafts/`, compiled from natural C. The exact target claims were in-memory diagnostic claims only; no canonical registry/ownership was changed.

- root `1C62:069E`: C `f_1C62_0090(); return 1;` compiles to the exact 8-byte target body, including its one fixup, while all existing root `1C62` peers and private data remain exact. At the raw DOS address, original and candidate agree for the callback-disabled and callback-enabled gate states. When enabled, both invoke `f_1C62_00A1` once and return 1; when disabled, neither invokes it and both return 1. This is direct differential evidence for the wrapper contract; it does not establish who calls the entry at runtime.
- root `1E57:0EB0`: C `clip_Push(); clip_Off();` compiles to the exact 9-byte target with its two fixups when inserted into canonical `src/root/m1E57.c` at the original order. The raw original/candidate entries execute the real original/candidate `clip_Push` and `clip_Off` bodies over both empty and one-rectangle-plus-sentinel clip lists. The heap allocator/handle-to-pointer/lock leaves are deterministic modeled boundaries, while `_fmemcpy` executes for the nonempty list. Final clip pointer, stack handle, depth, byte count, saved rectangles and ordered manager-service trace agree. The wrapper target and data claims are exact, but this insertion makes accepted peer `f_1E57_0F8E` inexact (75 vs 78 bytes); it therefore is not a whole-module acceptance. The earlier 83-byte scaffold draft is superseded by this canonical-source result.
- S04 `35F5:0980`: C `if (miniCursorOn) EraseMiniMapCursor(); else DrawMiniMapCursor();` compiles to exact 24 code bytes, four fixups, and one relocation; all existing peers and private data remain exact. Raw-address differential cases for initial `miniCursorOn` 0 and 1 agree on final flag, rectangle state and `f_1CE2_0410(rect,1)` trace. That rendering helper is modeled as a trace boundary, while the original/candidate Draw/Erase routines execute. The eight trailing zeros are outside this code body and remain unowned.

`*_wrapper-traces.json` files preserve the earlier bounded wrapper demonstrations. The rerunnable producer and stronger source/object/harness/component pins are in `reproducible-wrapper-proof/`. Its report includes 18 successful directed original-versus-candidate runs: six wrapper cases and four volatile/preserved-register canaries for each of three empty far-return entries. For the latter, natural C emits an exact one-byte `retf` at root `1E57:0008`, `23AE:037E`, and `284A:0137`; all recorded caller registers and SP agree. The 1E57 insertion also makes its accepted `f_1E57_0F8E` peer inexact, and the 284A insertion makes `f_284A_038F` inexact, so neither whole-module draft passes all accepted-peer gates. These are supplemental semantic demonstrations, not BEHAVIOR_EXACT registrations or promotable exact modules.

| root `1E57:0008` | Distinct no-op far-return entry; sequence between accepted empty far entries 0006/0007 and function 0009, and `/Gs` emits precisely the one-byte empty body. | Natural-C empty-function target bytes exact in diagnostic compile. No runtime caller evidence. Plausible callable empty function, not padding. |
| root `1E57:0EB0` | Real clipping wrapper: push current clipping state then turn clipping off. | Exact natural-C target bytes and modeled helper-order trace. Internal helper effect was not exercised in the trace. |
| root `23AE:037E` | Distinct `/Gs`-consistent empty far-return entry after `win_LockWin`; following zero is separate. | Empty-function interpretation is plausible. One trailing zero has no established owner or padding proof. |
| root `284A:0137` | Distinct `/Gs`-consistent empty far-return entry after `StopSong`, before `f_284A_0138`. | Plausible callable empty function; no runtime caller evidence. |
| S04 `35F5:0980` | Real mini-map cursor toggle: stack check, branch on private state, erase when set or draw when clear. | Exact natural-C target and bounded raw-address differential trace for both flag branches. Following eight zeros are not part of the function and remain unowned. |

The three executable wrappers are not absent/dead-code claims. They are unowned callable behavior identified at their actual addresses, suitable for a reviewed semantic supplement or a narrowly scoped supplemental-address runner. Registry/extent ownership remains a separate decision.
